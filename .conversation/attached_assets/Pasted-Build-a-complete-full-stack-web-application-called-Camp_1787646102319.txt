Build a complete full-stack web application called **CampusQuery — College FAQ Intelligence System**.

The application is a DBMS Level 3 experiential learning project. It must NOT be a simple CRUD application. The main purpose is to allow college students to ask university-related questions naturally and receive the most relevant answers from a structured and semantic knowledge base.

The project must satisfy the following academic requirements:

* Frontend: Next.js
* Backend/API: Next.js Route Handlers/API
* SQL database: PostgreSQL
* Vector database: PostgreSQL with pgvector
* Authentication and authorization with at least two roles: Student and Admin
* Proper database design with ER diagram-compatible relational schema
* Meaningful DDL and DML operations
* At least four advanced database concepts
* Secure environment-variable based configuration
* Database-level validation and integrity
* Functional and polished web interface
* Git/GitHub-ready project structure
* The application must clearly demonstrate why PostgreSQL and pgvector are both required

## 1. CORE PROJECT IDEA

Students frequently have difficulty finding information scattered across college websites, notices, academic regulations, department documents, FAQs, and administrative information.

Instead of requiring students to search manually, CampusQuery allows them to ask questions naturally.

Examples:

* "What is the minimum attendance required to write the semester exam?"
* "How do I apply for a bonafide certificate?"
* "When can I register for electives?"
* "What documents are needed for an internship approval?"
* "What is the procedure for applying for a re-exam?"
* "Where can I find information about hostel rules?"
* "What happens if my attendance falls below the required percentage?"

The system performs semantic/vector search over the FAQ and knowledge-base content and combines the result with structured PostgreSQL information.

The answer should show:

* Answer
* Relevant source/document
* Category
* Department
* Last updated date
* Similarity/relevance score
* Related questions

Do NOT build a generic chatbot that invents answers. Answers must be generated/retrieved from the application's stored knowledge base.

## 6. REQUIRED ADVANCED DATABASE FEATURES

Implement at least FOUR of the following, preferably FIVE:

### A. Transactions

Use PostgreSQL transactions for important operations such as:

* Creating an FAQ and its embedding.
* Publishing a document and creating its chunks.
* Deleting an FAQ and its dependent records.

### B. Views

Create useful SQL views such as:

1. popular_faqs_view
2. unanswered_or_low_feedback_faqs_view
3. department_faq_statistics_view

The admin dashboard should use at least one view.

### C. Stored Function / Procedure

Create at least one PostgreSQL function.

Example:

get_faq_statistics(department_id)

which returns FAQ count, average rating, views and feedback information.

### D. Trigger

Create a trigger that automatically updates updated_at whenever an FAQ or document changes.

Optionally create another trigger that increments an FAQ's view count.

### E. Indexing

Create appropriate indexes for:

* user email
* FAQ category
* FAQ department
* FAQ status
* FAQ updated_at
* search history user_id
* feedback faq_id

Also use pgvector indexing for embeddings.

### F. Full-text Search

Implement PostgreSQL full-text search as a fallback/secondary search mechanism.

Use PostgreSQL tsvector/GIN indexing where appropriate.

### G. Vector Similarity Search

This is mandatory for the semantic-search component.

Use pgvector to store embeddings and perform similarity search.

## 7. SEMANTIC SEARCH

The central feature of CampusQuery is semantic FAQ search.

When the student enters:

"How many classes can I miss before I am not allowed to take the exam?"

the system should find FAQs such as:

"What is the minimum attendance requirement?"

even though the wording is different.

Create embeddings for FAQ questions + answers and document chunks.

Use a suitable embedding model/API.

Make the embedding provider configurable through environment variables.

Do not hard-code API keys.

Store:

* embedding
* embedding_model
* source ID
* metadata

Use cosine similarity or another appropriate similarity metric.

Explain this clearly in the README.

3. Store chunks in DOCUMENT_CHUNKS.
4. Generate embeddings.
5. Store embeddings using pgvector.
6. Store metadata linking each chunk to its source document.

The system should be able to retrieve the original source when answering a question.
